# Restaurant Review Platform - API Contract

Last updated: 2026-11-10

**API version:** 1.0.0 (tutorial base) · **Backend:** Spring Boot 4.1.2, Java 25 · **Read with:** `PROJECT-BRIEF.md`

This document is the authoritative, human-readable contract for the Restaurant Review Platform REST API. It describes **what the code actually does**, checked by reading (not yet by running) the controllers, DTOs, services and `SecurityConfig` in the tutorial's finished backend. Where the build guide says something different, this document wins, and section 10 lists every difference.

Any client should be able to rely on this document alone. If the code changes how an endpoint behaves, this document changes too, with a dated entry in the change log (section 12).

## 1. Overview

### 1.1 Base URL

Every path in this document is **relative to a base URL ending in `/api`**. Where it says `GET /restaurants`, the request is `GET <base>/api/restaurants`.

| Calling from | Base URL |
| --- | --- |
| An HTTP client (Postman, curl) | `http://localhost:8080` |
| My own frontend (later) | Set in the frontend's configuration |

Treat the base URL as configuration, never as a hardcoded constant.

### 1.2 Content types

- Request and response bodies are **JSON** (`Content-Type: application/json`).
- Two exceptions: photo upload (`POST /photos`) is `multipart/form-data`, and photo download (`GET /photos/{id}`) returns the raw image bytes.

### 1.3 Authentication

Tokens come from **Keycloak**, realm `restaurant-review`. The backend accepts only tokens whose issuer is:

```text
http://localhost:9090/realms/restaurant-review
```

Send the token as a Bearer header:

```text
Authorization: Bearer <access_token>
```

**Public (no token needed):** every `GET` under `/restaurants/**` and `/photos/**`. **Everything else needs a valid token**, including all `POST`, `PUT` and `DELETE` calls.

A missing, expired or invalid token returns `401`. The body is empty; Spring Security adds a `WWW-Authenticate: Bearer` header (framework default, not custom code).

The backend reads these claims from the token to identify the user:

| Claim | Stored as |
| --- | --- |
| `sub` | `User.id` |
| `preferred_username` | `User.username` |
| `given_name` | `User.givenName` |
| `family_name` | `User.familyName` |

### 1.4 Conventions

| Convention | Rule |
| --- | --- |
| Field names | camelCase, for example `cuisineType`, `datePosted` |
| Restaurant ids | Strings generated by Elasticsearch, usually 20 characters long |
| Review ids | UUID strings generated by the server |
| Photo ids | The stored filename: a UUID plus the original extension, for example `"3f6c...e21a.png"` |
| Timestamps | ISO-8601 local date-time with **no time zone**, for example `"2025-03-04T05:12:44"`, in the server's local time |
| Times of day | `"HH:mm"` strings, 24-hour, for example `"09:00"`, `"22:30"` |
| Ratings | Review `rating` is an integer 1 to 5; restaurant `averageRating` is a decimal 0 to 5 |
| Null fields | Present with the value `null`, not omitted (Jackson default) |

## 3. Data shapes

These shapes are reused by several endpoints. Each endpoint section refers back to them by name.

### 3.1 `Address`

```json
{
  "streetNumber": "42",
  "streetName": "Baker Street",
  "unit": "2B",
  "city": "London",
  "state": "Greater London",
  "postalCode": "NW1 6XE",
  "country": "United Kingdom"
}
```

| Field | Rule on create and update |
| --- | --- |
| `streetNumber` | Required; must match `^[0-9]{1,5}[a-zA-Z]?$`, for example `"42"` or `"42a"` |
| `streetName`, `city`, `state`, `postalCode`, `country` | Required, not blank |
| `unit` | Optional |

### 3.2 `OperatingHours` and `TimeRange`

```json
{
  "monday":    { "openTime": "09:00", "closeTime": "22:00" },
  "tuesday":   { "openTime": "09:00", "closeTime": "22:00" },
  "wednesday": null,
  "thursday":  { "openTime": "09:00", "closeTime": "22:00" },
  "friday":    { "openTime": "09:00", "closeTime": "23:30" },
  "saturday":  { "openTime": "10:00", "closeTime": "23:30" },
  "sunday":    { "openTime": "10:00", "closeTime": "21:00" }
}
```

- Each day is optional; `null` or missing means closed.
- When a day is present, both `openTime` and `closeTime` are required and must match `^([01]?[0-9]|2[0-3]):[0-5][0-9]$`.
- The server does not check that `closeTime` is after `openTime`.

### 3.3 `Photo`

```json
{
  "url": "3f6c2a1e-9b7d-4c21-8e5f-0a1b2c3d4e5f.png",
  "uploadDate": "2025-03-04T05:12:44"
}
```

`url` is the photo's id: pass it to `GET /photos/{id}` to download the image, and send it in `photoIds` when creating a restaurant or review.

### 3.4 `User`

```json
{
  "id": "8a1d3c2e-5f6b-4a7c-9d8e-1f2a3b4c5d6e",
  "username": "testuser",
  "givenName": "Test",
  "familyName": "User"
}
```

Copied from the JWT when a review is written (section 1.3). It is not updated if the user later changes their details in Keycloak.

### 3.5 `Review`

```json
{
  "id": "c0ffee00-1234-4abc-9def-0123456789ab",
  "content": "Great ramen, friendly staff, a bit noisy on Friday night.",
  "rating": 4,
  "datePosted": "2025-03-04T19:30:00",
  "lastEdited": "2025-03-04T19:30:00",
  "photos": [ { "url": "...", "uploadDate": "..." } ],
  "writtenBy": { "id": "...", "username": "testuser", "givenName": "Test", "familyName": "User" }
}
```

`datePosted` and `lastEdited` are equal until the review is edited.

### 3.6 `Restaurant` (full)

Returned by create, get and update.

```json
{
  "id": "Xk2pQZUBd9f1yWm7Lh0c",
  "name": "Golden Dragon",
  "cuisineType": "Chinese",
  "contactInformation": "+44 20 7946 0000",
  "averageRating": 4.5,
  "totalReviews": 2,
  "geoLocation": { "latitude": 51.5072, "longitude": -0.1276 },
  "address": { "...": "Address, 3.1" },
  "operatingHours": { "...": "OperatingHours, 3.2" },
  "photos": [ "Photo, 3.3" ],
  "reviews": [ "Review, 3.5" ],
  "createdBy": null
}
```

- `averageRating` and `totalReviews` are calculated by the server, never sent by the client.
- `geoLocation` is set by the server from the address. In the base build it is a **random point inside Greater London**, not the real location.
- `createdBy` is always `null` in the base build (Project Brief, section 10).

### 3.7 `RestaurantSummary`

Returned by search. A lighter version of `Restaurant` without contact information, opening hours, location or reviews.

```json
{
  "id": "Xk2pQZUBd9f1yWm7Lh0c",
  "name": "Golden Dragon",
  "cuisineType": "Chinese",
  "averageRating": 4.5,
  "totalReviews": 2,
  "address": { "...": "Address, 3.1" },
  "photos": [ "Photo, 3.3" ]
}
```

### 3.8 `Error`

Every error produced by the application's own error handler has this shape:

```json
{
  "status": 404,
  "message": "The specified restaurant wasn't found"
}
```

Some errors come from the framework instead and have a different body or no body at all; section 8 lists which.

## 4. Restaurant endpoints

### 4.1 `GET /restaurants`

Search restaurants. **Public.** Every parameter is optional.

| Parameter | Type | Default | Meaning |
| --- | --- | --- | --- |
| `q` | string | none | Text matched fuzzily against `name` and `cuisineType` |
| `minRating` | number | none | Only restaurants with `averageRating` at or above this |
| `latitude` | number | none | Centre of a location search |
| `longitude` | number | none | Centre of a location search |
| `radius` | number | none | Search radius in **kilometres** |
| `page` | integer | `1` | Page number, **starting at 1** |
| `size` | integer | `20` | Results per page |

**Only one kind of search runs per request.** The server checks these rules in order and uses the first that matches:

1. `minRating` given and `q` empty or missing: rating filter only.
2. `q` given: fuzzy text search, also filtered by `minRating` (default 0).
3. `latitude`, `longitude` and `radius` all given: location search only.
4. Otherwise: all restaurants.

So a location is **ignored** whenever `q` or `minRating` is also sent.

Fuzzy search is an Elasticsearch `fuzzy` query, which compares the search text against single indexed words. It most likely works best with one lowercase word such as `sushi`; this is a reading of the query, not yet tested.

Response `200`: a page (section 7) of `RestaurantSummary` (3.7).

Errors: `page` below 1 most likely returns `500`, because the server builds an invalid page request (not tested).

### 4.2 `POST /restaurants`

Create a restaurant. **Token required.**

Request:

```json
{
  "name": "Golden Dragon",
  "cuisineType": "Chinese",
  "contactInformation": "+44 20 7946 0000",
  "address": {
    "streetNumber": "42",
    "streetName": "Baker Street",
    "unit": null,
    "city": "London",
    "state": "Greater London",
    "postalCode": "NW1 6XE",
    "country": "United Kingdom"
  },
  "operatingHours": {
    "monday": { "openTime": "11:00", "closeTime": "22:00" }
  },
  "photoIds": ["3f6c2a1e-9b7d-4c21-8e5f-0a1b2c3d4e5f.png"]
}
```

| Field | Rule |
| --- | --- |
| `name`, `cuisineType`, `contactInformation` | Required, not blank |
| `address` | Validated as `Address` (3.1) when present |
| `operatingHours` | Validated as `OperatingHours` (3.2) when present |
| `photoIds` | At least 1 photo id from `POST /photos` |

`address` and `operatingHours` are not marked as required in the code, so a request without them passes validation. Send them anyway.

Response `200`: the stored `Restaurant` (3.6), with a new `id`, `averageRating: 0`, `totalReviews: 0` and a generated `geoLocation`.

Errors: `400` validation (section 8), `401` no token.

### 4.3 `GET /restaurants/{restaurantId}`

One restaurant in full, including all its reviews. **Public.**

Response `200`: `Restaurant` (3.6).

Errors: `404` with an **empty body** for an unknown id.

### 4.4 `PUT /restaurants/{restaurantId}`

Replace a restaurant's details. **Token required.** Same request body and rules as `POST /restaurants` (4.2). This is a full replacement, not a partial update: send every field.

What the server keeps and what it replaces:

| Kept | Replaced |
| --- | --- |
| `id`, `reviews`, `averageRating`, `createdBy` | `name`, `cuisineType`, `contactInformation`, `address`, `operatingHours`, `photos` |

`geoLocation` is generated again from the new address, so in the base build it moves to a new random point. Every photo's `uploadDate` is reset to the time of the update.

Response `200`: the updated `Restaurant` (3.6).

Errors: `404` `{"status": 404, "message": "The specified restaurant wasn't found"}`, `400` validation, `401` no token.

### 4.5 `DELETE /restaurants/{restaurantId}`

Delete a restaurant and all its reviews. **Token required.**

Response `204`, no body. **An unknown id also returns `204`**, so a delete is safe to repeat.

Errors: `401` no token.

## 5. Review endpoints

Reviews always belong to one restaurant, so every review path starts with `/restaurants/{restaurantId}/reviews`. An unknown `restaurantId` returns `404` `{"status": 404, "message": "The specified restaurant wasn't found"}` on every endpoint in this section.

### 5.1 `GET /restaurants/{restaurantId}/reviews`

List a restaurant's reviews. **Public.**

| Parameter | Default | Meaning |
| --- | --- | --- |
| `page` | `0` | Page number, **starting at 0** (unlike restaurant search) |
| `size` | `20` | Reviews per page |
| `sort` | `datePosted,desc` | `datePosted` or `rating`, then `,asc` or `,desc` |

Examples: `?sort=rating,desc` (best first), `?sort=datePosted,asc` (oldest first), `?page=1&size=5`.

An unknown sort field falls back to `datePosted`. Only the first sort field is used.

Response `200`: a page (section 7) of `Review` (3.5). A page past the end returns an empty `content` list, not an error.

### 5.2 `POST /restaurants/{restaurantId}/reviews`

Write a review. **Token required.** The author is the user in the token.

Request:

```json
{
  "content": "Great ramen, friendly staff, a bit noisy on Friday night.",
  "rating": 4,
  "photoIds": ["9c4e7a12-88fd-4b0e-a1d3-2f6b9c0e4a55.jpg"]
}
```

| Field | Rule |
| --- | --- |
| `content` | Required, not blank |
| `rating` | Required, integer 1 to 5 |
| `photoIds` | Optional; defaults to `[]` |

Response `200`: the new `Review` (3.5). The restaurant's `averageRating` is recalculated.

Errors:

- `400` `{"status": 400, "message": "The specified review cannot be created or updated"}`: this user has already reviewed this restaurant.
- `400` validation (section 8).
- `401` no token. `404` unknown restaurant.

### 5.3 `GET /restaurants/{restaurantId}/reviews/{reviewId}`

One review. **Public.** Used by the edit review page.

Response `200`: `Review` (3.5).

An unknown `reviewId` returns **`204` with no body**, not `404`.

### 5.4 `PUT /restaurants/{restaurantId}/reviews/{reviewId}`

Edit a review. **Token required.** Same request body and rules as 5.2.

The server replaces `content`, `rating` and `photos`, sets `lastEdited` to now, and recalculates the restaurant's `averageRating`. `datePosted` never changes.

Response `200`: the updated `Review` (3.5).

Errors: all three cases below return the same `400` body, `{"status": 400, "message": "The specified review cannot be created or updated"}`:

- the review does not exist;
- the caller is not the review's author;
- more than 48 hours have passed since `datePosted`.

Also `400` validation, `401` no token, `404` unknown restaurant.

### 5.5 `DELETE /restaurants/{restaurantId}/reviews/{reviewId}`

Delete a review. **Token required.** The restaurant's `averageRating` is recalculated.

Response `204`, no body. An unknown `reviewId` also returns `204`.

**Any signed-in user can delete any review.** Unlike update, delete does not check the author (section 10).

Errors: `401` no token, `404` unknown restaurant.

## 6. Photo endpoints

Photos are uploaded **first**, on their own. The returned `url` is then sent in `photoIds` when creating or updating a restaurant or review.

### 6.1 `POST /photos`

Upload one image. **Token required.** `multipart/form-data` with one field:

| Field | Type | Rules |
| --- | --- | --- |
| `file` | file | Must not be empty. The original file extension is kept. |

Response `200`:

```json
{
  "url": "3f6c2a1e-9b7d-4c21-8e5f-0a1b2c3d4e5f.png",
  "uploadDate": "2025-03-04T05:12:44"
}
```

The file is saved as `uploads/<uuid>.<extension>` on the backend's disk.

Errors:

- `500` `{"status": 500, "message": "Unable to save or retrieve resources at this time"}`: empty file, or the file could not be written.
- `401` no token.

**Not checked in the base build:** file type (any file is accepted) and file size. Spring Boot's default upload limit is 1 MB per file; a larger file most likely returns `500` "An unexpected error occurred" (framework default, not tested).

There is no `caption` field, although the guide's API overview mentions one.

### 6.2 `GET /photos/{id}`

Download an image. **Public**, so a plain `<img src="/api/photos/<id>">` works.

`{id}` is the full `url` value from 6.1, extension included, for example `/photos/3f6c2a1e-9b7d-4c21-8e5f-0a1b2c3d4e5f.png`.

Response `200`: the raw image bytes, with:

- `Content-Type` guessed from the file extension, or `application/octet-stream` if unknown;
- `Content-Disposition: inline`, so browsers display it instead of downloading it.

Errors: `404` with an empty body for an unknown id.

## 7. Pagination

Both list endpoints return a Spring Data `Page` serialised as-is. The project does not define its own page shape, so this is the framework's default JSON, shown here with the fields that matter:

```json
{
  "content": [ "...items..." ],
  "pageable": {
    "pageNumber": 0,
    "pageSize": 20,
    "offset": 0,
    "paged": true,
    "unpaged": false,
    "sort": { "sorted": true, "unsorted": false, "empty": false }
  },
  "totalElements": 42,
  "totalPages": 3,
  "number": 0,
  "size": 20,
  "numberOfElements": 20,
  "first": true,
  "last": false,
  "empty": false
}
```

| Field | Meaning |
| --- | --- |
| `content` | The items on this page |
| `number` / `pageable.pageNumber` | Current page, **always counted from 0** in the response |
| `size` | Page size requested |
| `totalElements` | Total items across all pages |
| `totalPages` | Total number of pages |
| `first`, `last` | Whether this is the first or last page |

**Watch the page numbering.** `GET /restaurants` takes `page=1` for the first page, but its response still says `"number": 0`. `GET .../reviews` takes `page=0` for the first page.

## 8. Error code summary

Errors from the application's `ErrorController` use the `Error` shape (3.8). Rows marked "framework" come from Spring itself and have no `Error` body.

| Status | When | Body |
| --- | --- | --- |
| `400` | Validation failed on a request body | `{"status": 400, "message": "<field>: <reason>, <field>: <reason>"}` |
| `400` | Review already exists, review not found on update, not the author, or past 48 hours | `{"status": 400, "message": "The specified review cannot be created or updated"}` |
| `401` | Missing, expired or invalid token on a protected endpoint | Empty (framework) |
| `404` | Unknown restaurant on update, or on any review endpoint | `{"status": 404, "message": "The specified restaurant wasn't found"}` |
| `404` | Unknown restaurant on `GET /restaurants/{id}`, unknown photo | Empty |
| `500` | Photo could not be stored, or the file was empty | `{"status": 500, "message": "Unable to save or retrieve resources at this time"}` |
| `500` | Any other unexpected error | `{"status": 500, "message": "An unexpected error occurred"}` |

A validation message joins every failed field, for example:

```json
{
  "status": 400,
  "message": "rating: Rating must be between 1 and 5, content: Review content is required"
}
```

The order of fields in the message is not guaranteed.

There is **no `403`** anywhere in the base build: the API has no roles and only one ownership check (review update), which returns `400`.

## 9. Business rules

### 9.1 One review per user per restaurant

A user is identified by the token's `sub` claim. If any review on the restaurant already has `writtenBy.id` equal to the caller's `sub`, `POST .../reviews` returns `400`. Deleting the review frees the user to write a new one.

### 9.2 The 48-hour edit window

A review can be edited only while the server's current time is no later than `datePosted` plus 48 hours. The window is measured from `datePosted`, not `lastEdited`, so editing a review does not extend it.

### 9.3 Average rating

`averageRating` is the plain mean of all review ratings, recalculated and saved after every review create, update and delete:

```text
averageRating = (rating_1 + rating_2 + ... + rating_n) / n
```

With no reviews it is `0`. It is never rounded by the server, so `4.333...` is possible; the client decides how to display it.

### 9.4 Photos are references

`photoIds` are stored as given. The server does **not** check that a photo with that id was ever uploaded. Upload the photo first (6.1) and send its exact `url` value.

### 9.5 Geolocation

In the base build, every create and update gives the restaurant a **random point inside Greater London** (latitude 51.28 to 51.686, longitude -0.489 to 0.236), whatever the address says. Location search therefore works, but positions are not real.

## 10. Where the code differs from the guide

The build guide was written alongside a live build, and some of it no longer matches the finished code. **When they disagree, follow the code**, which is what this contract describes.

| Topic | Guide says | Code does |
| --- | --- | --- |
| Path prefix | API overview lists `/restaurants`, `/photos` | Every path starts with `/api` |
| Review update path | `PUT /reviews/{reviewId}` | `PUT /api/restaurants/{restaurantId}/reviews/{reviewId}` |
| Public access | `permitAll()` on `/api/restaurants/**` for every method | Only `GET` is public; `POST`, `PUT`, `DELETE` need a token |
| `cuisineType` search filter | Listed as a query parameter | Not implemented |
| Search page size | 1 to 100 | Not enforced |
| Review sort values | `date,desc`, `rating,asc`, ... | `datePosted,desc`, `rating,asc`, ... |
| Review page numbering | Default page `1` | Default page `0` |
| Review page size | 1 to 50 | Not enforced |
| Photo `caption` | Optional upload field | Not accepted and not stored |
| Validation message | Starts with `"Validation failed: "` | Field errors only, no prefix |
| Storage error message | "Unable to save or recall the resource at this time" | "Unable to save or retrieve resources at this time" |
| Review not found on update | Throws `ResourceNotFoundException` (never defined) | `400` with the review-not-allowed message |
| Edit window | One lesson says 24 hours | 48 hours |
| Review service method names | `getRestaurantReviews`, `getRestaurantReview` | `listReviews`, `getReview` |

Gaps that are not differences but are worth knowing (no owner checks on restaurants or review delete, `createdBy` never set, location ignored alongside `q`) are listed in the Project Brief, section 10.

## 11. curl quick start

A five-minute walkthrough from a bash shell, run from `restaurant-backend/`. It needs the Docker services and the backend running, and the Keycloak setup from the Project Brief, section 7.

```bash
BASE=http://localhost:8080/api
KC=http://localhost:9090/realms/restaurant-review
```

**1. Get a token from Keycloak:**

```bash
TOKEN=$(curl -s -X POST $KC/protocol/openid-connect/token \
  -d grant_type=password \
  -d client_id=restaurant-review-app \
  -d username=testuser \
  -d password=password \
  | python3 -c "import sys, json; print(json.load(sys.stdin)['access_token'])")
echo "$TOKEN"
```

This uses Keycloak's password grant, which works only if **Direct access grants** is switched on for the `restaurant-review-app` client. If the client is confidential, also send `-d client_secret=...`.

**2. Upload a photo and keep its id:**

```bash
PHOTO=$(curl -s -X POST $BASE/photos \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@src/test/resources/testdata/golden-dragon.png" \
  | python3 -c "import sys, json; print(json.load(sys.stdin)['url'])")
echo "$PHOTO"
```

**3. Create a restaurant and keep its id:**

```bash
RID=$(curl -s -X POST $BASE/restaurants \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Golden Dragon",
    "cuisineType": "Chinese",
    "contactInformation": "+44 20 7946 0000",
    "address": {"streetNumber": "42", "streetName": "Baker Street", "city": "London",
                "state": "Greater London", "postalCode": "NW1 6XE", "country": "United Kingdom"},
    "operatingHours": {"monday": {"openTime": "11:00", "closeTime": "22:00"}},
    "photoIds": ["'"$PHOTO"'"]
  }' \
  | python3 -c "import sys, json; print(json.load(sys.stdin)['id'])")
echo "$RID"
```

**4. Search without a token:**

```bash
curl -s "$BASE/restaurants?q=chinese"
curl -s "$BASE/restaurants?minRating=4&page=1&size=10"
```

**5. Write a review:**

```bash
curl -s -X POST $BASE/restaurants/$RID/reviews \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"content": "Excellent dumplings.", "rating": 5, "photoIds": []}'
```

Expect `200` with the new review. Run the same command again and expect `400`: one review per user per restaurant.

**6. Read it back:**

```bash
curl -s "$BASE/restaurants/$RID/reviews?sort=rating,desc"
curl -s "$BASE/restaurants/$RID"   # averageRating is now 5.0
```
